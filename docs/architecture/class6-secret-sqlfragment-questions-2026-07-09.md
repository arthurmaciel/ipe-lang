## §0 — Blocking contradictions / stale premises (resolve first)

1. The #44 plan defers Auth re-typing because "the registry has no
   `Auth.signToken`/`verifyToken` kernels" — but those kernels now EXIST
   (`crates/sky_kernels/src/lib.rs:983-984,2119-2120,3015-3016`; schemes at
   `crates/sky_types/src/constrain.rs:4878-4883`, pinned by AUD-06). Does
   #44's scope now include Auth re-typing, or does the deferral survive
   despite its stated premise being gone? If deferred, does that violate
   CLAUDE.md §4 no-deferral given "secrets are typed" is the whole point?
2. **`Secret` per plan is inadmissible in a Sky.Live Model** — no
   `PartialEq`/`Hash`/serde (`2026-07-02-secret-type.md:158,188-189`), but
   the Live Model gate requires `Serialize+DeserializeOwned+Clone+PartialEq`
   (SKY-L0120, `crates/sky_backend_rust/src/emit_model_gate.rs:6-19`) and
   the session store serializes the whole Model
   (`runtime/src/sky_runtime/live/store.rs:193`). Is Model-inadmissibility
   the DESIGNED semantics (secrets never persist to session stores), and if
   so where does a Live app hold a long-lived secret? The plan never
   addresses this at all.
3. CLAUDE.md §8 says "Auth.signToken/verifyToken take `String`, not `any`"
   — re-typing to `Secret` supersedes the letter while honoring the spirit
   (already framed as sanctioned divergence in the plan). Who updates §8's
   text + `docs/divergences-from-sky.md`, and does the Go-oracle comparison
   for Auth fixtures survive (excluded from byte-diff, or fixture calls
   `Secret.fromString` at the boundary)?
4. The #61 sketch cites `SqlIdent`'s `[A-Za-z0-9_]` parse for `column` —
   but two validators exist with DIFFERENT alphabets: `SqlIdent::parse`
   rejects `.` (`db.rs:1135-1137`) while `valid_sql_ident` accepts `.` for
   table-qualified names (`db.rs:1768-1773`, used by the newer typed-field
   paths). Which alphabet gates `SqlFragment.column`? Without `.`,
   `users.id` is unrepresentable.
5. The #61 sketch specifies `struct SqlFragment { sql, binds: Vec<SqlValue> }`
   — but `SqlValue` is a SYNTHETIC Sky-side enum generated by the lowerer
   (`crates/sky_lower/src/lower.rs:3172-3234`); the runtime's actual
   binding type is the 6-variant `SqlParam` (`db.rs:1708-1721`), with a 9→6
   collapse performed in GENERATED code
   (`crates/sky_backend_rust/src/project.rs:813-826`). Where does the
   collapse happen for fragments, and what's the emit-boundary
   representation of a synthetic-enum value flowing into the `param`
   kernel (the existing collapse is keyed to specific `Db.exec`/`query`
   call shapes)?
6. Is the 2026-07-02 plan authoritative/guardian-reviewed input, a draft to
   re-validate, or superseded? Determines whether this stage is "review +
   patch" or "design from scratch informed by it."

## §1 — Opaque-type pipeline mechanics (every new opaque type must decide)

Grounding trace done by the asker: `Decimal` = kernel builtin (canon
`EXTRA_BUILTIN_TYPE_NAMES`, `crates/sky_canon/src/resolve.rs:148-151`; IR
leaf `IrType::Decimal`, `crates/sky_ir/src/ir.rs:692-698`; rendered
`sky_runtime::decimal::Decimal`, `crates/sky_backend_rust/src/emit_types.rs:77`;
runtime newtype `Clone,Copy,PartialEq,Eq,Ord,Debug,serde`,
`runtime/src/sky_runtime/decimal.rs:8-10`). `Money` = pure-Sky ADT
(`crates/skyc/stdlib/Std/Money.sky:46-47`). `SqlValue`/`SqlField` = a
THIRD path: lowerer-synthesized enums. The #44 plan picks the
Decimal/Bytes-leaf path; the #61 sketch picks an interned `Ty::Con` +
kernels.

7. Three registration paths exist — which does each item take, and why?
   Is `Ty::Con` with zero registered constructors sufficient opacity for
   SqlFragment, or does canon need an explicit "no constructors, no field
   access, no destructuring" rule for these names?
8. **Where is constructor privacy actually enforced?** `resolve.rs:645`
   builds export surface from `exposing (…)`; `NameNotExposed` exists
   (`resolve.rs:387`) — but nobody verified `exposing (T)` (without
   `(..)`) actually hides constructors cross-module in the Rust port. If
   it doesn't, the "pure-Sky opaque module" fallback is unsound for either
   type. **Verify with a failing-import test before choosing a path.**
9. `ir_type_is_derivable` (`ir.rs:795-840`): a Clone-only `Secret` joins
   non-derivable leaves (Task/Cmd/Db/Fun). A record containing a Secret
   loses `#[derive(Clone,Debug,PartialEq…)]`
   (`emit_types.rs:409-436`). Is `==` on a Secret-containing RECORD a clean
   skyc-side type error (does `ty_is_equatable`, `sky_types/src/lib.rs:493`,
   recurse into records?), or exit-0-then-cargo-fail (the exact class
   #45/#70 exist to close)? Same question for SqlFragment if non-derivable.
10. Adding ~4 (Secret) + ~18 (SqlFragment) kernels multiplies the
    `StdlibKernel::ALL`/`decl().arity` drift surface (#45/#70,
    `backlog.md:66`, "no completeness tripwire"). Should #45/#70 land
    first, or do these items add their own per-family tripwires?
11. Confirm no parser/lexer change needed for either (both use only
    qualified names + kernel machinery) — and if SqlFragment wants
    operator-ish combinator names, does that assumption still hold?
12. New diagnostic codes (plan mints SKY-T0014): does each ship its
    explain page in the same change, and is SKY-T0014 also right for
    raw-String-where-SqlFragment-expected, or is that ordinary SKY-T0001?
13. Both are pre-push security tier — every new symbol gets caught by the
    #59 rename. Name them Sky-style now and let the mechanical rename
    catch them, or is either name rename-sensitive?

## §2 — #44-specific: Secret semantics

Plan settles: sealed `Secret(String)`, redacting `Debug`, no `Display`,
redacting `SkyStringify`, no `PartialEq`/`Hash`, four kernels
(`fromString`/`reveal`/`redacted`/`constantTimeEq`), `==` rejected at
SKY-T0014, zeroize optional. Open questions the plan does NOT settle:

14. Construction trust levels — dominant source is an env var
    (`SKY_AUTH_TOKEN_SECRET`). Should `System.getenv` grow a
    Secret-returning companion (`getenvSecret`) so plaintext never
    transits a plain `String`, or is `Task.map Secret.fromString`
    acceptable? Is a string LITERAL passed to `fromString` (committed
    secret smell) in scope for a lint?
15. Payload type: String or Bytes? `Secret(String)` can't hold a binary
    HMAC/AES key without base64 gymnastics.
16. Stringify redacts, equality errors — asymmetric strictness. Should
    toString/interpolation of a Secret ALSO be a type error (with
    `Secret.redacted` as explicit escape), matching the no-silent-coercion
    rule (CLAUDE.md §8), or is silent redaction on stringify the
    principled line?
17. Dict-key/Set-element behavior: no Hash — clean SKY-coded error naming
    Secret, or generic obligation failure? Same for `List.member`/`sort`
    (Eq/Ord obligations).
18. Post-`reveal` responsibility boundary: a revealed String can flow into
    `Log.errorWith`/`Error.unexpected`/Task error text. Accepted residual
    risk, or should `Log.*`/`Trace.*` accept `Secret` directly
    (auto-redacting) to shrink the window?
19. `constantTimeEq` implementation — reuse `subtle::ConstantTimeEq` (the
    ancestor's CSRF crate) or hand-roll; does a naive length check leak
    length in this threat model?
20. Zeroize is marked deferrable in the plan, but security tier is
    "before the push" and hardening never defers per memory. Decide
    explicitly: hardening (ships now) or additive (may defer)?
21. WASM hooks: does #44 ship the transitive-Secret-containment predicate
    for `HydrationState` now (even unused), and is `Secret.fromString`/
    `reveal` client-legal under `--target wasm` (client may hold ITS OWN
    secrets) or server-only?
22. Auth re-typing shape (once §0-Q1 resolved): which argument becomes
    `Secret`, do `verifyToken`/JWT/console-HKDF follow in the same change,
    and what migrates the 39-example sweep fixtures passing String today?

## §3 — #61-specific: SqlFragment semantics

Sketch settles: opaque type, no `raw : String -> SqlFragment`, leaf
constructors `column`/`param`/`int`/`string`/`lit`, comparison/boolean
combinators, `inList`/`like`/`group`, consumers `findWhere`/`deleteWhere`.
Current injection surface it must close: `db_unsafe_find_where`
interpolates the WHERE clause verbatim (`db.rs:1438-1456`); everything
else already binds positionally via sqlx or gates identifiers.

23. Is `lit` load-bearing or a liability — every whitelisted operator is
    already covered by a typed combinator, so a whitelist is still a
    string-shaped door future maintenance can widen. Drop `lit` entirely
    (add `isNull`/`orderBy` as typed kernels instead), or keep it? If
    kept, checked at compile time or runtime kernel-call time (runtime
    reject turns injection into a 500, weakening "SQL injection = type
    error")?
24. Precedence soundness: should every combinator emit `( … )`
    unconditionally, making explicit `group` redundant by construction
    (forgetting `group` today is a representable correctness bug)?
25. Empty `inList col []` — SQL syntax error in SQLite/Postgres. Compile-
    impossible shape, runtime `Err`, or safe `FALSE`?
26. Combinator naming (`and_`/`or_`/`not_` trailing underscores dodge
    Prelude collision, but Sky style elsewhere never uses trailing
    underscores) — qualified-only (`Sql.and`), different words
    (`both`/`either`), or keep underscores? Check parser/canon reserved
    names before deciding.
27. Consumer scope: sketch adds `findWhere`/`deleteWhere` only, but
    `updateFields`'s WHERE is equality-only, `insertFieldsReturning`'s
    projection is a validated raw String, and the upstream audit pairs
    #61 with RETURNING "so projections can't reopen injection." State the
    scope-creep line explicitly in the design doc: findWhere/deleteWhere
    only? `updateWhere`? typed projection? ORDER BY/LIMIT fragments?
28. Fate of `unsafeFindWhere` — sketch says "documented as legacy…
    eventually deny-flagged," but pre-push security framing + no-deferral
    norm cut the other way. Remove/deprecate now, gate behind a project
    flag, or leave it (accepting the injection surface stays
    representable, weakening the "type error" headline for un-migrated
    code)?
29. Dialect portability: fragments accrete `?`-text; Postgres uses `$N`
    and is currently structurally unreachable (AUD-09). Does the fragment
    store dialect-neutral placeholders translated at consume time, so
    #61 doesn't hard-code SQLite into a security type right before
    Postgres reachability gets fixed?
30. Fragment equality/printing — `==`-comparable (useful in tests)? Does
    Debug/toString show bind values (user data — and if a bind is a
    revealed Secret, this intersects #44's Q16 redact-vs-reject decision)?
31. `param : SqlValue -> SqlFragment` ergonomics — users construct
    SqlValues today only in literal list position for `Db.exec`; passing
    one into a KERNEL as a bare arg is new. Does existing lowering handle
    a synthetic-enum value flowing into a kernel arg, or is this new
    lower/emit work the sketch's "~18 kernels" estimate omits?

## §4 — Shared machinery

32. One "restricted-ops opaque builtin" mechanism, or two hand-wired
    ones? Both need: interned type name, canon qualifier, IrType/`Ty::Con`
    leaf, non-equatable/non-stringify policy, kernel family, runtime
    newtype. Should the design introduce a per-type capability table
    (equatable? stringifiable? serde? dict-key?) consulted by
    unify/stringify/model-gate — so a THIRD opaque type is a table row,
    not another arm-hunt — or is that over-engineering for n=2?
33. Consistent restricted-op diagnostics — one code with per-type explain
    text, or one code per restriction class, across Secret-`==`,
    Secret-as-Dict-key, Secret-in-HydrationState (future),
    SqlFragment-`==` (if rejected), raw-String-into-`findWhere`?
34. Fuzzer coverage: do both items land with new negative-fuzzer
    categories (secret `==` → SKY-T0014; string-where-fragment → expected
    code) and positive templates (fragment round-trip no-panic)?
35. Oracle/golden strategy: neither type exists in Go Sky, so byte-diff
    oracle can't cover them. Self-oracle goldens only (like `m5b_db_*`)
    plus divergence-ledger entries — does #35's sweep gate need a
    "divergent-feature fixture" lane so these don't silently fall outside
    the source-of-truth gate?
36. Ordering between the two items: SqlFragment reuses landed
    `SqlValue`/`valid_sql_ident`/sqlx-bind machinery; Secret's main
    downstream (Auth re-typing, WASM gate) is partially blocked on §0
    decisions. Which lands first, and do they share a branch (both touch
    `sky_kernels` enum ordering — the plan itself warns about discriminant
    shifts under parallel work)?
