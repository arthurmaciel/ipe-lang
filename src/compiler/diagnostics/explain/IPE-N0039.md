# IPE-N0039: a CustomElement boundary type parameter is not a plain, closed value type

`CustomElement` is the reserved Ipê type that names the typed boundary between
an Ipê app and a JavaScript-backed visual widget — a map, a chart, a
date-picker. A binding typed `CustomElement down up` names, in its two type
parameters, the *down-state* handed down to the widget and the *up-event* the
widget sends back:

```ipe
codeEditor : CustomElement EditorState EditorEvent
```

Every value that crosses this boundary is turned into data (encoded) on the way
out and read back from data (decoded) on the way in — the same way a form field
or a saved-page snapshot already crosses between Ipê and the browser. For that
to be safe and possible, each of the two parameters must be a **plain, closed
value type**: a value made only of data, with a fully-known shape.

The plain value types are: the primitives (`Bool`, `Int`, `Float`, `String`,
`Char`, `Bytes`), records, lists, tuples, `Maybe`, and your own declared types
built out of those — all the way down. Anything else is refused here, before it
can reach the boundary:

```ipe
-- rejected: a function is not data and cannot be sent across the boundary
picker : CustomElement (Int -> Int) String

-- rejected: a Secret must never be exposed to JavaScript
form : CustomElement Secret String

-- rejected: the boundary is concrete — a type variable has no fixed shape
generic : CustomElement a String
```

## Why each of these is refused

- **A function** (`a -> b`) is behaviour, not data. There is no way to send a
  function to the browser as a value, so it cannot cross the seam.
- **An effect** (`Cmd`, `Task`, `Sub`) is a pending action, not a finished
  value; it has no data form to cross with.
- **A view value** (`Html`, `Element`, `Attribute`) is a rendered-tree
  description tied to the Ipê runtime, not a boundary data value.
- **A `Secret` or a reserved sink type** (`SqlFragment`, a CSS-safety marker) is
  a security-tier value. Handing one to JavaScript would leak the very thing the
  type exists to protect, so it is refused by rule (Security before everything).
- **A type variable or an open record** leaves the shape unknown. The boundary
  is *concrete*: the compiler generates one exact encoder/decoder per exact
  type, with no guessing at run time.

## How to fix

Make each parameter a plain, closed type. Declare a small record or a simple
data type that holds exactly the fields the widget needs, and name that:

```ipe
type alias EditorState =
    { text : String, cursor : Int }

type EditorEvent
    = TextChanged String
    | CursorMoved Int

codeEditor : CustomElement EditorState EditorEvent
```

Both `EditorState` and `EditorEvent` are made only of primitives, so every value
crossing the boundary has a known shape and a total encode/decode form.

## Glossary

- **seal** — the rule that every value crossing the Ipê↔JavaScript boundary must
  be a plain, closed, concrete value type. It is what makes the boundary typed
  instead of an untyped hole.
- **down-state / up-event** — the value handed *down* to the widget, and the
  value the widget sends *up* as an event.
- **concrete** — a type with no leftover unknowns (no type variables, no open
  records), so exactly one encoder and decoder can be generated for it.
- **sink type** — a type (like `SqlFragment` or a CSS-safety marker) that carries
  a value into a security-sensitive place, and is deliberately not serialisable.
