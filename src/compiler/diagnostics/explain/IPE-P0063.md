# IPE-P0063: invalid path literal

A `path "…"` literal contains a string that fails compile-time path validation.
The two rejection cases are:

**NUL byte** — the string contains a `\0` character. A NUL byte terminates a
C string at the syscall boundary, so `"safe.txt\0../../etc/passwd"` reaches the
kernel as `"safe.txt"` on some code paths and as the full string on others —
a classic poisoned-NUL bypass.

**Traversal escape** — the string's lexically-cleaned form starts with `..` or
`../`, meaning a relative path that climbs above the directory it is resolved
against. For example `"../etc/passwd"` and `"a/../../secret"` both escape. A
rooted path beginning with `/` can never escape (the `Clean` algorithm stops
`..` at the root) and is always accepted.

## Rejected examples

<!-- illustrative-only: Ipê source syntax, not runnable shell commands -->

A string that escapes via `..` is rejected with IPE-P0063:

```ipe
bad = path "../etc/passwd"
```

A string with a NUL byte (`\0`) is also rejected:

```ipe
dangerPath = path "safe\0bad"
```

A relative path that resolves above its base after cleaning is also rejected:

```ipe
escapedAfterClean = path "a/../../secret"
```

## Fix

Replace the literal with a path that stays within its base:

```ipe
good = path "src/Main.ipe"
```

A rooted path is always accepted — `..` cannot climb above `/`:

```ipe
absolute = path "/usr/share/data.json"
```

If the path is not known at compile time, use `Path.fromString` and handle
the `Result`:

```ipe
fromUserInput : String -> Result Error Path
fromUserInput s = Path.fromString s
```
