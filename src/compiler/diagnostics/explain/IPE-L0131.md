# IPE-L0131: a row-polymorphic record annotation is not yet emittable

A function was annotated with a **row-polymorphic** record type — a record type
that names a few required fields and leaves the rest open with a row variable:

```ipe
-- `r` is the row variable: "any record that has AT LEAST a `name` field"
getName : { r | name : String } -> String
getName rec =
    rec.name
```

The type `{ r | name : String }` reads as: "a record carrying a `name : String`
field, plus any other fields, which the variable `r` stands in for." A record is
a small bundle of named values, like `{ name = "Ada", age = 36 }`. Row
polymorphism lets one function accept every record that has the fields it needs,
no matter what extra fields ride along.

The type checker understands this type completely, and the program is
well-typed. The gap is in the **backend** — the stage that turns your Ipe code
into Rust. To generate Rust for `getName`, the compiler must know the *exact*
set of fields of the record it receives, because each distinct record shape
becomes its own Rust `struct`. A row-polymorphic parameter deliberately does not
fix that set, so the backend cannot yet pick one struct to emit.

## How to fix

**Give the function a closed record type** that lists every field the callers
actually pass. A closed type has no row variable:

```ipe
-- accepted: a closed record type — the exact field set is known
getName : { name : String, age : Int } -> String
getName rec =
    rec.name
```

**Or drop the annotation** and let the compiler infer the type. Without a
signature, the field access `rec.name` still works, and the compiler pins the
parameter to whatever concrete record you pass at the one call site:

```ipe
-- accepted: no signature; the compiler infers a concrete record shape
getName rec =
    rec.name
```

## Why this happens

Ipe's Rust backend represents each record shape as a dedicated `struct`, keyed
by its exact, sorted field set. That keeps the emitted code concrete and fast —
no runtime field lookup. A closed annotation, or an inferred type pinned at a
single call site, hands the backend one exact field set, so it emits one struct.

A row-polymorphic annotation is different: the same function may be called with
`{ name, age }` at one site and `{ name, id }` at another, so there is no single
field set to emit. Supporting it soundly needs the backend to emit a separate
specialised copy of the function per record shape it is called with — a planned
extension. Until it lands, the compiler stops here rather than emit Rust that
would fail to build after `ipe build` already reported success.
