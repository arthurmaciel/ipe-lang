# IPE-N0040: a decoder pipeline is hand-nested instead of threaded with `|>`

The decoder-pipeline combinators — `Db.Decode.required` / `optional` and
`Json.Decode.Pipeline.required` / `optional` / `requiredAt` / `custom` — build a
decoder one field at a time, applying the fields to a constructor. Each
combinator takes the decoder built so far as its **last** argument and applies
that constructor to the field it just decoded.

Written as a hand-nested application, the **innermost** combinator is the one
whose value reaches the constructor's **first** parameter — so the field written
**first** in the source binds to the constructor's **last** parameter. The
binding is silently reversed:

```ipe
-- WRONG: hand-nested. "a" binds to the ctor's LAST parameter, "b" to its first.
decoder =
    DbDecode.required "a" fieldA
        (DbDecode.required "b" fieldB
            (DbDecode.succeed (\a b -> ( a, b ))))
```

When two adjacent fields share a runtime type (both `String`, both
`Maybe String`, …), no type error can catch the swap, so the program compiles
and returns quietly wrong data. That silent-reversal footgun is why this form is
rejected.

Thread the decoder with the forward pipe `|>` instead. The accumulator flows the
other way, so the field written first binds to the constructor's first
parameter — source order matches parameter order:

```ipe
-- RIGHT: piped. "a" binds to the ctor's FIRST parameter, "b" to its second.
decoder =
    DbDecode.succeed (\a b -> ( a, b ))
        |> DbDecode.required "a" fieldA
        |> DbDecode.required "b" fieldB
```

The JSON pipeline reads the same way, and `optional` / `requiredAt` / `custom`
thread identically:

```ipe
userDecoder =
    JsonDecode.succeed User
        |> JsonDecodePipeline.required "name" JsonDecode.string
        |> JsonDecodePipeline.optional "age" JsonDecode.int 0
        |> JsonDecodePipeline.requiredAt [ "address", "city" ] JsonDecode.string
```

Prefer the pipe form everywhere: the field order you write is the field order
you get. This diagnostic rejects the directly hand-nested application spelling —
one combinator applied straight to another as its last argument — which is where
the reversal hides in practice.
