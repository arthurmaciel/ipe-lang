# IPE-N0037: a reserved Ipê↔JS boundary type is used before its transport ships

This code is **dormant**. It once rejected any use of the reserved
`CustomElement` boundary type outright, before its two type parameters were ever
inspected. The compiler now does something more precise, so this exact code is
no longer produced — but it is kept in the taxonomy so older references still
resolve, and this page explains what replaced it.

`CustomElement` is the reserved Ipê type that names the typed boundary between an
Ipê app and a JavaScript-backed visual widget. A binding typed
`CustomElement down up` names, in its two type parameters, the sealed
*down-state* handed to the widget and the *up-event* the widget sends back:

```ipe
codeEditor : CustomElement EditorState EditorEvent
```

Two checks now replace the single blanket rejection. First, each of the two type
parameters must be a plain, closed value type — the seal. A function, a `Secret`,
a type variable, or another non-plain type is rejected with **IPE-N0039**:

```ipe
-- rejected with IPE-N0039: a function cannot cross the boundary as data
picker : CustomElement (Int -> Int) String
```

Second, a `CustomElement` value that type-checks still cannot be built until its
widget transport ships; that is a clean **IPE-L0133** at code-generation time,
not a silent acceptance:

```ipe
-- type-checks, then rejected with IPE-L0133: transport not shipped yet
editor : CustomElement Int String
editor = editor
```

The name stays *reserved*: you cannot define your own `type CustomElement` to
work around the boundary — that remains a separate rejection, **IPE-N0026**.
Together these keep the original guarantee — no untyped value ever crosses the
Ipê↔JavaScript boundary — while teaching the specific rule broken rather than a
single blanket "not yet".
